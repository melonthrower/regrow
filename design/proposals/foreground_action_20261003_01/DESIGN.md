# 前景接管时的动作约束设计 v3

本稿交原需求对话和 Astra 审查，**仅为提案，未实现、未部署、未恢复 GUI**。源码基线固定为私有 `melonthrower/regrow` 的 `19448694bdc1db14aa863b04a378c8c28a93ea65`；具体位置见 [CHANGE_MAP.md](CHANGE_MAP.md)。本轮新增 0 HTTP / 0 GUI。原运行和上一批交付均只读。

建议在现有动作绑定的接受边界补上“当前交互对象”检查：历史身份关联和交互资格分别判断，资格未知不能借 `association.unconfirmed` 获得执行许可。继续使用现有 `BindingConflict → revise / observe / defer`，不另建审核角色、纠错循环、调度器或应用特例。

## 真实经过和根因

原运行：`artifacts/runs/clock_complete_20261002_01/run`。

## 最小实现范围

增加一个小文件 `action_interaction.py`，只负责从已有记录投影证据、判断当前动作资格；不是第二套身份库或动作执行器。拟议接口为 `project(run, records, state, request)`、`refresh(request)`、`check(request, proposal, association)`，名称可在实施前调整。绑定仍由 stepwise_flow 负责，纠错、观察、登记仍走原流程。

### 一份只读证据投影

在正常 `assemble_current_context` 的任务/导航目标确定后，投影到内部 `interaction_context`：

- snapshot、observation、来源调用、登记图 SHA、实际选点图 SHA；前景范围及其依据是否已经在当前图重新核对。
- 当前可交互 Region、当前观察的 control_refs、已接受的 foreground 及相关动作的 region_changes；保留明确 blocked、not_visible、uncertain 的区别。
- 稳定的任务 Region/control，以及导航的 working_region、return_to 和相关入口。0165 依靠 r0016，而非不存在的 task_control。
- 这些目标及相关已知背景控件的合格身份/点击区域和观察出处，作为**限制或消歧线索**，不加入可点击候选。当前活跃对象继续使用现有 backend_candidates、visual_choices 与模板质量规则。

旧坐标、名称、历史状态和匹配分数各自都不能单独定资格。目标未列入 interactive_regions 可能只是尚未定位；只有当前前景、当前视觉对应及已接受的接管/范围证据一致时，才认定它在被接管背景。字段缺失、模板不合格、候选截断或层级矛盾均保留未知。

### 换帧核对

`target_observation.refresh` 同时更新位置表与上述证据；`repair_stages.refresh` 和普通 run_task_step 调用它，避免不同入口另算一套范围。

同 SHA 的已接受范围可以复用。异 SHA 不仅检查菜单裁图：建议在原 `foreground_scope` 的正常发现/更新输出中增加可空的 `context_bbox`，表示**包含前景、被接管背景及相关弹出层的完整应用交互上下文**，不能只圈菜单或按钮。随原观察保存，不建第二套缓存。审计要求它包含本次 interactive_areas、当前受限目标的可见位置及观察中的相关应用容器；不能确认完整边界时为空，按整屏处理。旧记录缺该字段不猜测补齐，须沿正常观察取得当前依据。这是待原需求对话确认的唯一范围协议扩展。

跨 SHA 复用必须同时满足：截图尺寸、前台窗口依据及容器位置未变；上述完整 context 在相同坐标**逐像素不变**；上下文外的变化只落在该正常观察已明确排除的非交互系统显示区，且无覆盖层/输入归属矛盾；当前对象仍由现有 matcher 或本帧接受的观察明确定位。仅有整屏排除框、窗口信息未知或变化用途不明，均不满足外部变化条件。这里没有新相似度阈值、移动变换或自动忽略区域；一个熟悉图标和整屏 same_surface 不构成通过依据。任何应用内变化、移动、可能新增覆盖层、模板缺失/多解均回正常 observe/relocalize，再按新观察判断新对象。

本例 a0033 after→a0034 before 只有 76 个变化像素，a0034 before→pre_dispatch 只有 69 个，均在 [706,8,714,18] 的顶部时钟文字内；这是离线像素事实，**不证明交互归属**。原 0161 没有合格完整 context/明确系统区分框，不能据此静默给旧记录补通过。实施后的正常观察可记录完整应用上下文和系统显示区，再验证是否支持该复用；否则补观察、保留额度耗尽缺口。应用内时钟/动画会多补观察，是首版明确代价。不能在 load=None 时放行，也不能用菜单旧框封锁新前景对象。

### 所有动作绑定分支共用检查

在 `bind_action_target` 外层统一检查 `_bind_action_target` 的初步关联结果，覆盖精确名称、改写名称后的点位匹配、弱候选、布局关联和 unconfirmed 兜底；还要约束会改变界面的键盘、输入及指针动作。none 和单纯 wait 保留原观察路径。身份 matched 不自动等于交互 allowed。

检查次序：

1. **先确认当前前景实际对象。** 有当前前景对象证据时，使用它的 owner、身份和点击范围。新前景对象可以占用旧背景坐标；旧背景坐标或历史名字不能抢占它。前后对象确有竞争且不能分层时进入观察消歧，不强绑旧控件。
2. **阻止已知被接管背景业务。** 当前图能对应已知背景对象且它不属于当前可交互表面时，返回 unresolved/BindingConflict，不走未关联身份兜底。检查稳定身份、当前点位证据和工作/导航目标关系，不依赖 target 的拼写。把按钮改叫“新入口”“空白”“关闭菜单”不能授权它。
3. **保留未知对象探索。** 新对象不要求历史模板、控件 ID 或候选表命中。最低依据是唯一当前截图上明确的对象/落点、该帧已核对的可交互表面、没有相反的已知对象或层级证据；仍按原 unconfirmed 登记，不强赋旧身份。坐标在范围内是必要条件，不单独证明对象角色。视觉定位或前后归属有歧义时 observe；不是把整个候选表变成白名单。
4. **准备动作是当前有依据的另一操作。** 当前前景中可定位的关闭/返回控件正常绑定；已确认菜单或对话框上的平台 back（桌面 Esc、Android 系统返回）可用于退回准备，效果仍待后图。其他 key_press/hotkey 在接管状态下须有当前接收对象依据：正常观察的焦点/选中对象，或本次可靠聚焦回执及当前对象核对。还须有该具体键/组合与该对象的对应依据，例如当前已观察的快捷键提示或同上下文、同对象的真实键动作结果；焦点明确不证明应用级快捷键路由。路由不明则观察/保留缺口。历史可作补充，不能独立证明当前焦点。Enter/Delete/任意快捷键不能仅把 reason 写成“关闭”就许可。没有前景接管或对象冲突时继续既有键盘契约，不新增通用键盘语义系统。
5. **菜单外空白点击不作名称豁免。** 仅在已有真实关闭/返回动作及当前表面对应支持、当前落点确认为非业务操作区时沿用其准备依据；历史点必须在当前重新定位，且不得落入已知背景业务点击区。纯色空白不能伪造为合格控件模板。无此证据时先 observe，或选择有依据的 back/关闭控件。a0032 的 Ring 关闭证据不能只因两菜单相似就自动授权 Snooze 任意外点；上一批新 Luna 选择 (700,641) 也尚无新执行效果。

这是同一资格检查的三类结果：可交互对象继续绑定；有依据的准备动作带 preparatory_action 继续；证据矛盾或不足进入原纠错。准备标记从实际对象、动作及依据派生，不接受模型声明豁免。hover、drag 及 Android scroll 检查实际起点/终点和所属表面；桌面 scroll 的 end_x/end_y 表示方向，不能当屏幕终点。none/wait 不变。即使没有控件身份，交互资格也不能为空而默认为允许。

### 投递和结果仍用原流程

`repair_stages.accept_candidate` 将资格拒绝送入既有 BindingConflict，携带当前前景、限制对象稳定引用、实际候选及来源，不新增 blocked_by 枚举。`context` 披露限制对象，`observe_registered` 重新定位后回原任务；不清零原 2 次纠错 / 1 次补观察限制。改名、edit_record 或重复声明不能在同一份证据上消除冲突。

在 `run_task_step` 取得 pre_dispatch 图后重建当前证据并重新绑定/检查；不可继续把旧 binding 原样当作 fresh binding。失败复用 `reject_action`，不投递 GUI，不把最新图确认当永久豁免。自动 `visual_backtrack` 的导航也调用同一资格函数；它仍使用自己的真实导航回执及落点观察，不新增并行审核机制。

`action_commands.execute` 的输入不是一次投递：首次聚焦、已知输入目标的自动再次聚焦、全选、文字发送均复用该资格判断。`input_target.resolve` 的同对象视觉匹配不证明当前接收输入。首次聚焦前检查；after_focus/after_retarget 后若表面变化或接收对象不确定，停止剩余命令，保留已执行 click、原额度和 `text_delivered=false`，让正常 update/observe 处理部分效果；不能抛掉回执、自动再点一次或提前记输入完成。再次聚焦须在它自己的当前图上重新检查；文字阶段须确认当前接收对象可交互。

**首版建议保守分步，不豁免聚焦边框、光标或选中状态的应用内变化。** 原测试允许边框变化后同次输入；本方案可能先只完成聚焦，登记后再由正常观察确认焦点和前景，从新请求继续原输入任务。已聚焦且当前完整上下文稳定、接收对象明确时可同次输入。光标持续变化导致无法通过或原额度不足，须明确报告该正常路径未接受；不能宣称边框测试原行为仍保持。验收必须展示整条合法输入最终成功的原生路径，不能只测安全停止。是否另允许有充分当前证据的聚焦样式变化在同次内部继续，由原需求对话决定；在此之前不把 same_target 当豁免。执行器内不新增模型纠错循环。

准备动作保持原工作目标，来源记真实前景/未关联对象，不冒挂背景业务控件。沿 `build_attempt_update → commit_update → settle_task / task_result_review` 只登记后图实际变化。`settle_task` 当前 same_object 只比身份，未比较本次 operation/preparatory_action；supported 历史只需非空结果描述，也可能包含“已投递但无效果”。因此本次业务完成还须核对任务要求的操作和本笔实际效果；**同控件上的准备操作也不能作为业务完成证据**。历史独立完成链可满足累计任务，但普通回执/无效果描述不能充当该链；若原结果核对尚未确认，就走原 task_result_review、保持 pending。建议局部补结算证据条件，不改任务 schema、不扫描改写历史。这里是静态发现的相邻风险，不声称已有原生复现。本批不改写 a0034、a0035 或任何旧完成记录。

## 方案取舍

推荐上述资格检查。只加 prompt 不能证明会拒绝坏提案；只拒绝未匹配目标会损伤未知对象和准备路径；仅将点击点限制在菜单矩形也无法处理外部准备、换帧、前景新对象及键盘路径。新增每步独立视觉审核模型则会形成平行机制和固定额外调用，本轮没有必要。

## 可能影响及待讨论

- 当前模型范围偏小、旧观察缺前景字段、无合格模板的合法控件，会增加纠错/观察；不应永久禁用它们。原观察额度耗尽仍保留缺口。
- 菜单外准备和普通键盘操作比原兜底严格；优先保证有依据的 back/关闭路径可用，外点无证据时不冒险猜测。是否接受这作为首版边界，由原需求对话审查。
- 是否接受正常 foreground 增加可空完整 context，以及上述严格跨帧条件？它对应用内动态变化会增加观察；原记录缺字段必须补观察。若不接受协议扩展，首版只能按完整同帧证据处理，并先验证原观察额度是否足够，不能暗用整屏相似放宽。
- 菜单外空白首次无真实关闭历史时是否允许：本稿推荐先用有依据的 back/前景关闭，不能把“看起来空白”当效果保证；这是拟议首版边界，并非已接受的用户规则。
- 是否接受合法输入因聚焦边框/光标变化先分步登记，再补观察继续？这是当前严格换帧政策的实际影响；若持续动态变化阻止输入，方案须修订再接受，不能用安全停止冒充功能完成。
- 图导航、输入、hover/drag/scroll 要共用资格检查，但不拓展到生产级全面兼容或一般任意键盘语义理解；仍遵守原平台/范围限制。
