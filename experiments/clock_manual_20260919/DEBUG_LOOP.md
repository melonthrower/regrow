# 遍历—修复闭环

在现有三步遍历器外增加 `debug_loop.py`。输入已有应用清单（apps 下的 key/run）和一个新的输出目录；原图、设备、额度及动作恢复语义不变。一个监督进程用两个运行槽按最近调度时间轮转单步运行；候选修复串行，避免与旧连续运行抢设备。每轮归档结果；用户创建输出目录下 STOP 后，不再发起下一轮，当前回合使用原暂停入口收尾。

停止分类优先顺序：用户暂停/额度 → 基础设施或服务等待 → 真实未解决步骤 → 所有区块完成验证。region_complete 仅表示一个区块，不能直接等同整图完成。没有区块、待结算动作、暂挂、清点不完整或功能登记缺口都不能算完成。

框架错误产生独立问题目录，关联截图、请求、回复、运行日志、图快照和冻结源码。不复制全部历史。同设备共享文件锁，并检查已有遍历进程；不抢占正在运行的旧队列。每应用的 kind＋stage 归一为修复签名，累计最多三次候选修复，服务错误不改框架。

修复在独立候选目录完成。修复代理只改临时框架及新增针对性测试；候选需通过：程序执行测试、陌生读者独立理解、独立意图对照、真实Luna保存帧重放及其语义检查、受影响应用单轮现场试跑。测试或审查报告绑定候选源码哈希。失败保留全部证据，原源码不改，先处理其他应用。候选只通过离线验证时不得称GUI成功。

候选试跑会真实更新图；不回滚图或重放动作。失败只撤回源码选择，保留运行结果并交下一轮正常结算。候选成功后作为该应用的新冻结版本；其他应用按各自停点验证，不全局热更新。源码变更另存，不自动改工作目录、提交或推送。

实现顺序：状态/完成判定与问题归档 → 候选修复及验收 → 监督入口 → 定向测试/陌生读者/实际模型验证。验证先用小样本；本入口不启动新设备、不绕过平台服务拒绝，不把未启动应用算遍历完成。

## 使用
在开发机使用 guiwalk-android Python 运行 `debug_loop.py <应用清单.json> <新的监督输出目录>`。清单格式复用现有 `{"apps":[{"key":"vlc","run":"绝对run路径"}]}`。再次使用同一输出目录会读取保存状态。创建 `<输出目录>/STOP` 暂停；移除后重启可继续用户暂停，预算暂停不自动续期。

状态在 `status.json`，变化在 `events.jsonl`；每轮入口/日志在 `rounds/`，每个问题/候选/审核/模型答复在 `issues/`，初始冻结源码在 `sources/`。预算沿用manifest中的session_limits且跨轮累计，保存帧Luna也计入HTTP；无上限时不另设遍历总调用限额。开发/读者Codex会话单独保留调用及usage事件，每应用每 kind＋stage 累计最多三轮，每会话15分钟；不将这些会话数冒充Luna HTTP数。两个已卡在截图等待的设备仍会占满两个槽，需暂停等待中的设备再扩大调度；本版不创建或修复VM。

最终complete仅表示当前已发现图全部清点、任务/功能登记满足条件、没有待发现/待结算/恢复状态。界面可能存在尚未发现的入口，仍不声称数学意义穷尽。needs_attention、service_blocked、paused和waiting均不是完成。


已通过某应用现场试跑的候选，按“原源码哈希＋问题签名”缓存。相同基线的其他应用可复用，但各自仍须试跑；同应用失败过的版本不反复套用。首次候选尚在试跑时，并发另一应用仍可能独立开发，不能声称严格并发去重。保存帧验证的临时HTTP错误最多原请求重试三次，每次计账；持续失败保留候选并标service_blocked，不继续用改代码处理服务故障。

独立阅读清单排除开发笔记和旧审核；意图对照仅决定是否进入Luna验证，不能要求下一关结果提前存在。上一轮候选被拒绝的理由只提供给开发者。候选源码在试跑前及推广前都核对哈希，未结算或repair_pending不推广。

本轮修正：错误额度按每应用的 kind＋stage 累计三次，解释措辞变化不另开额度；旧问题计数恢复时合并保留，不清零。进度摘要加入功能复核有效性，并移入 debug_progress.py，由所选候选动态加载。旧冻结版本无此文件时使用监督器模块、仍读取旧任务实现。停滞验收用候选算法同时计算试跑前后，算法改变本身不算进展。常驻 debug_loop.py/debug_candidate.py 不允许自动候选修改，需外部验收重启。保存帧调用显式定位仓库导入依赖。
