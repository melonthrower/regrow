# VLC 七步例子：我们要怎样探索和组织 GUI

这是用户已确认意图的详细例证，供新对话理解探索目标。它不是新增框架设计、VLC专用规则、固定点击脚本或本应用已经完整验收的证明。当前实现以`CURRENT_FRAMEWORK.md`及模块文档为准，实验停止点以`SERVER_HANDOFF.md`为准。

读完后应能回答：本页有哪些区块、哪些具体控件表达哪些功能、哪些信息已经可见、哪些未知关系值得探索、哪些部分可以跨页共享，以及怎样支持后续复杂指令和实机采集。

## 1. 用这一个页面理解组织方式

用户讨论的是VLC的Simple Preferences窗口，以Interface分类为例。下面是预期的内容组织，不是要求每一层都产生一次调用或一个独立执行任务：

```text
当前可交互前景：Simple Preferences
├─ 分类导航：Interface / Audio / Video / …
├─ 当前分类内容：Interface settings
│  ├─ Look and feel
│  │  ├─ 样式选择：Native / Custom
│  │  ├─ Native条件下的设置：如Force window style
│  │  └─ Custom条件下的设置：如Skin source file
│  ├─ Playlist and Instances
│  └─ Privacy / Network Interaction
└─ 底部固定区域
   ├─ Show settings：Simple / All
   ├─ Reset preferences
   ├─ Save
   └─ Cancel
```

边界和层级由当前画面及实际变化确认，不按这些标题匹配。底部独立固定的证据可能要滚动后才得到；初次粗分区应允许依据新证据修正。Save等是可登记控件，是否执行仍取决于本次实验授权；登记不等于必须点击。

## 2. 七步探索分别要得到什么

| 步骤 | 观察/探索 | 希望记录的内容 |
| --- | --- | --- |
| 1. 识别前景 | 当前能接收输入的是Simple Preferences | 前景范围及其中可交互内容，避免把背景播放器控件混进当前清单 |
| 2. 初步分区 | 分类导航、Interface内容和其子区；底部边界可后续完善 | 区块及父子归属，不把整扇窗口永久当一个不可拆的大区块 |
| 3. 控件与功能清点 | 定位具体控件；展开未知有限下拉列表 | 控件owner与功能分别表达。例：“设置媒体切换提示显示时机”，其参数列表在实际展开后记录 |
| 4. 模式关系探索 | 切Native/Custom，比较选中状态与内容变化，必要时安全恢复 | “选择界面样式”的互斥参数；Native下哪些子设置可用，Custom下哪些子设置可用；附实际观察来源 |
| 5. 滚动补齐并修正边界 | 查看Privacy区未展示部分；观察底栏是否固定 | 新出现的不同功能、滚动内容的归属、固定底栏的独立区块身份；不重复登记已见内容 |
| 6. 切换分类并复用 | 点击Audio后检查哪些部分保留、隐藏、出现或改变 | 复用仍存在的导航/底部区，登记Audio内容；把变化与实际点击关联，不复制共享区块的同一控件任务 |
| 7. 后续按图采集 | 完成Audio中的业务后，识别同屏可见的Show settings | 目标区块可见且可交互就直接使用；只有目标不可见时才需要图指导导航 |

上表是理解顺序，不是固定的七次调用或七次GUI动作。一次观察可以登记多层信息；功能清楚的普通值可只记录，未知值域或改变功能结构的模式才安排必要探索。不要为了“证明每个功能”逐项切换所有复选框或逐值应用下拉选项。

## 3. 功能分组不等于合并物理控件

- 一个独立复选框背后的设置可以是一个功能；该复选框本身仍需要独立、可定位的控件身份。
- Native和Custom是两个物理点击入口，可以共同表达“选择界面样式”这个功能的两个参数值。不能因功能归组，就把两个落点合成一个含糊owner。
- 圆形按钮和一选一未选可以支持“可能互斥”的假设，不能单凭外观保证它们属于同组。点击后观察另一项取消选中，才获得这次互斥行为的证据。
- 模式切换显露另一套配置，说明探索应发现条件子功能。不要把所有模式入口都当作普通参数值跳过，也不需要因此新增递归任务调度器。

自然语言记录可类似：

> 功能：选择界面样式。参数：Native、Custom。观察到选择Custom后Native取消选中，同时出现皮肤文件选择设置；该设置属于Custom条件下的子功能。各选项仍引用自己的当前控件。记录所依据的截图/动作，并分别保存历史观察与最近确认值。

“Show media change popup”的Never、When minimized、Always来自用户当时的例子；本说明不将它们晋升为新运行已经展开核验的结果。其他尚未观察的参数应明确写未知，不能凭熟悉软件补全。

## 4. 必须分清的四种关系

| 关系 | 例子 | 不能混淆成什么 |
| --- | --- | --- |
| 包含 | Interface settings包含Look and feel等子区 | 不能把每个层级都当成需要点击进入的独立页面 |
| 参数互斥/条件可用性 | Native或Custom；皮肤文件设置依赖Custom模式 | 不能只保留两次孤立点击，丢掉二者关系；也不能把推测写成已验证约束 |
| 动作造成的变化 | 点击Audio后Interface内容被Audio内容替换 | 不能仅凭前后截图差异就忽略外部变化或虚构按钮因果 |
| 同屏可见/共享 | Audio内容与底部Show settings同时存在 | 不能强造Audio→底栏的因果边，也不能因为没有这条边而要求先回Interface |

不同分类下的持久导航应共享身份和同一操作任务，实际点击仍绑定当前画面的控件。初次错误地将导航、主体、底栏合成一个区块，后续应能根据独立滚动/内容替换证据细化，保留旧观察及引用对应关系，不改写原始动作。Simple/All切换后的结构仍须实看，不假定所有旧区块都继续存在。

## 5. 应当怎样向用户展示探索结果

用户希望能看到Luna当前的分区、发现的控件/功能、已知参数与关系，以及还准备探索什么和为什么；不是只展示下一次点击。

框架应检查编号唯一性、引用/归属、当前绑定及重复任务。用户检查语义是否符合页面和目标，不要求用户肉眼审查所有编号。区分已直接观察、依据动作确认、仍是假设/未知，不用历史参数摘要冒充当前状态。

## 6. 当前实现与这个例子的距离

以下是本地同步时已知状态，后续以新证据和当前模块说明更新，不能把目标全部打勾：

- 已有RegionOccurrence父子归属、Element观察来源、层级和功能目录导出；Luna在Video有限页已有局部实机正例。
- `db8beaec`已经修正同CanonicalOperation的普通Task复用/收敛，并改进区块候选召回；它没有完成任意历史粗区块的自动重分配。
- 持久导航是否正确独立分区，仍可能漂移。旧播放器/Playlist顶部菜单归属就是下一轮实测卡点；不能把不同主体整体合并来消除重复。
- 互斥和条件含义主要保留为自然语言加证据，不代表已有完整机器约束求解器，也不代表所有下游生成/采集都已正确使用这些关系。
- 这个例子是通用组织形式的说明。不能把示例答案塞给Luna、硬编码VLC标题或固定点位，让单个案例看似通过。
