## 通用判定规则与正反例

一般规则：
1. 按用户结果命名。能说清“对什么对象，达成什么结果”，才是任务能力；点击、输入、滚动、打开入口仅是操作或路由，不能单独冒充业务任务。
2. 保持一个区块内的完整目的。把服务于同一对象和同一结果的控件组织在一起，不按按钮拆任务；同区块中有不同目的的能力也不能强行合并。多个独立业务区块协作留给后续组合。已有证据确认的参数弹层可关联，但不能为了凑完整任务扩大区块身份。
3. 完成边界明确且有依据。说明完成时应出现什么内容、状态、产物或答案。草稿、预览、未启动状态也可以是终点；不一律要求保存，不以“已点击”“已到达”代替业务结果。描述能力的完成条件不等于宣称已经执行成功。
4. 保存约束槽位，不实例化指令。登记可设置属性、已观察类型/值域、条件及所在区块/控件；具体目标值留到后续指令生成。已观察的枚举值可以保存，不能把其中一组值固化为本次业务任务。
5. 粒度不以步骤多少决定。一个设置修改也可构成任务；多个操作也可能仅为导航。去掉按钮动作描述后仍有明确用户结果，才值得进入业务目录。
6. 严格依据探索证据。只记录明确可见或已探索确认的能力；直接观察不要求额外执行。无法支持对象或结果时不登记该能力；已支持的能力仍有局部限制未确认时写unconfirmed，不补猜提交、持久化或组合兼容性。

正反例（只示范粒度，不是当前应用已有事实，也不能复制例子中的能力或值域到记录）：
| 正例：可登记的任务能力 | 反例：不适合作为本阶段业务目录项 | 原因 |
| 配置计时器时长，停在未启动状态；约束为时长 | 点击数字键、输入数字、打开计时器页 | 操作/到达没有表达完整结果 |
| 填写联系人草稿，保持未保存；约束为姓名、电话等 | 逐个登记“填写姓名框”“点击电话框” | 同一草稿目的不按控件拆分 |
| 修改默认文字大小，使设置反映目标字号 | 选择下拉框；或笼统写“设置” | 前者只有操作，后者没有对象和结果；修改一项设置也可完整 |
| 查询符合条件的日程，得到对应事件列表；约束为日期范围 | 输入搜索词、打开日历 | 查询得到的内容是结果，输入和导航只是手段 |
| 配置当前闹钟；约束为已观察的时间、周期、振动、标签 | 创建周六07:00、标签早饭的闹钟 | 后者提前选择了具体参数；本阶段只登记能力和约束 |
| 分别登记笔记编辑区的保存笔记能力、消息区的发送消息能力 | 把“写笔记并发送给联系人”登记为一个区块内的任务 | 多个独立业务区块协作属于后续组合 |
| 只确认了草稿填写时，登记草稿能力并保留保存缺口 | 只看见编辑框就登记“成功保存并同步” | 结果超出了已观察证据 |

这些规则与正反例分别保存在功能识别/单区块任务判定规则.prompt、功能识别/单区块任务正反例.prompt，仅由区块功能登记调用加载。框架验证结构、引用和流程；语义粒度由Luna依证据判断，不采用关键词黑名单。
