# 控件提示词：详细分块版

本文件用于维护控件对象的提示词。保留完整解释、正反例和局部字段示例；每次调用只提取需要的规则块，再与本次材料、任务和输出格式组合。

## 组装说明（不发送给模型）

### 1. 固定边界与稳定 ID

每个规则块都用独占一行的 HTML 注释包围。开始标记包含 `id` 和 `requires`；结束标记重复同一个 `id`。标记之间的全部正文属于该块，包括标题、解释和示例。

- `id` 是程序提取使用的稳定标识。调整中文标题或文档顺序时，不改变它。
- `requires` 是该块必须同时加载的其他块 ID，以英文逗号分隔；没有依赖时为空字符串。
- 块不嵌套，ID 不重复。正反例及其前提留在所属块内，不再单独切开。
- 块外文字、边界标记及依赖信息只供维护和组装使用，不进入模型提示词。它们不是模型需要输出的新字段。

建议程序先按本步职责和允许输出的字段选择 ID，再递归补齐依赖、去重，最后按本文顺序连接各块正文。读取时检查开始与结束 ID 一致、依赖存在且无循环；不要通过中文标题层级猜测边界。

### 2. 按本步职责选择

| 本步需要的说明 | 直接选择的块 |
|---|---|
| 控件身份与本次区块关联 | `control.identity` |
| 稳定名称与描述 | `control.name_description` |
| 识别所得的用途推测 | `control.knowledge_initial` |
| 根据操作结果更新用途知识 | `control.knowledge_result` |
| 修订已有知识条目 | 在相应知识来源块之外，加 `control.knowledge_revision` |
| 知识项的参数规则 | 在相应知识来源块之外，加 `control.knowledge_constraints` |
| 主要功能入口、是否仍需探索 | 按实际字段分别选 `control.may_open_content`、`control.needs_exploration` |
| 本步直接给出身份图范围 | `control.bbox` |
| 请求追加另一种身份外观 | `control.add_image` |
| 判断当前动作是否可执行 | `control.action_availability` |
| 新增访问路线、修订旧路线条件 | 按实际操作分别选 `control.jump_new`、`control.jump_revision` |
| 任务信息归属、原问题是否完成 | 按职责选 `task.ownership`、`task.completion` |

这些是选块入口，不是每类调用的固定字段清单。依赖会自动补齐，不需要重复列出基础块；加载说明也不扩大本步允许输出的字段。

任何调用只要实际输出 `controls[].index / region_index`，都同时选择 `control.references`；仅返回已指定对象的局部字段、不输出这些引用时，无需额外加载。需要判断复用还是新建时，选择 `control.identity`，它会自动带入引用说明。

`knowledge_initial` 与 `knowledge_result` 按知识来源选择。若同一步既确认实际操作对象的用途，又登记新出现控件的用途推测，可以同时加载；前者依据动作结果，后者仍是识别推测。不能按整个调用阶段把所有知识统一视为确认。

固定选块配方还应检查：选择 `control.knowledge_revision` 或 `control.knowledge_constraints` 时，必须按实际知识来源同时选择 `control.knowledge_initial`、`control.knowledge_result` 中至少一个。依赖闭包只补齐共同基础，不替调用配方决定知识来源。

### 3. 两个最小组合示例

仅补充已有路线的条件时，选择：

`["control.jump_revision"]`

补齐依赖后得到输出约定、控件定义、条件约定、跳转基础和旧路线修订。不会因此加载新增目标规则，也不要求本次重新打开旧目标。

根据操作结果更新用途、修订旧知识并回答原任务时，选择：

`["control.knowledge_result", "control.knowledge_revision", "task.completion"]`

若本次回复还要填写 `controls[].index / region_index`，再选择 `control.references`；需要判断是否复用已有控件时选 `control.identity`。本次没有新增路线或图片请求，就不因此附带相应说明。

### 4. 接入时统一确认的约定

以下内容应与实际接收端、调用格式保持一致。它们在这里集中说明，不作为要求模型补字段或执行额外动作的指令。

- 本文按增量更新编写：未提交的对象属性和旧知识、旧路线保留；没有更新不等于清空。若接收端使用整项替换，应由实际协议或适配层明确补全要求。
- 本文将条件数组解释为“各项同时成立”；`[]` 表示所述范围内没有额外已知条件。若现有消费者采用其他语义，先统一约定。
- 用途推测、已确认用途及其修订应保留实际来源。本文不新增来源或置信度字段，也不假定接收端已经支持同一回复内按不同对象区分来源；若目前只能按调用阶段区分，应通过现有流程分别登记。
- `constraints` 的外层容器、每步必填字段、观察与疑问的输出位置、截图来源，以及 `bbox / add_image` 的阶段安排，沿用真实调用格式。本文件只补充语义，不另造一套 schema。

## 组合示例（不发送给模型）

下面示例仅帮助维护者理解两个路线块如何同时使用，不构成额外的独立规则块。

前提：同一个顶部“＋”按钮的旧路线 0，已在世界时钟页验证为打开城市选择，但漏写条件；本次又实际在闹钟页打开新建闹钟，并把新目标放在 `regions[1]`。同时选择 `control.jump_revision` 与 `control.jump_new` 后，可在同一回复中保留旧路线修订和本次新增目标：

```json
{
  "jump_to": [
    {
      "index": 0,
      "conditions": ["世界时钟标签页已选中"]
    },
    {
      "region_index": 1,
      "description": "点击顶部新增按钮后打开新建闹钟。",
      "conditions": ["闹钟标签页已选中"]
    }
  ]
}
```

第一项只补旧路线条件，不声称本次访问城市选择；第二项记录本次实际到达的新目标。所有编号仍以本次真实材料和输出列表为准。
