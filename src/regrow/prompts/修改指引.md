# 修改 Prompt 去哪里

## 维护原则

全部 17 类调用已使用按目的与实际字段组合的出口。`调用/*.prompt` 维护本步目的；四个 `对象/*.prompt` 维护可复用概念、字段含义和正例；`流程/调用组成.json` 的 `field_sections` 声明组合关系。调用之间共用含义，不各写一版字段解释。

最终顺序为：角色与运行范围 → 本步目的 → 必要概念 → 相关字段说明、正例与局部格式 → 当前专用补充。普通纠错另外保留原调用的已发送要求。`prompt_sections` 是审计元数据，不是 Luna 的输出字段。

同名字段按完整路径区分。例如，控件知识的 constraints 是参数说明对象，功能的 constraints 是已有参数引用列表；不能只凭字段名选说明。`when_values` 让 resume 等枚举说明随真实能力出现，`when_request` 区分完整与局部 proposal。

## 字段与格式如何组合

例如，下列字段组只在本次确实可以更新控件知识时出现：

```json
{
  "block": "control.knowledge_revision",
  "fields": ["controls"],
  "when_paths": ["controls.knowledge"],
  "details": [
    {"block": "control.knowledge_description", "when_paths": ["controls.knowledge.description"]},
    {"block": "control.knowledge_index", "when_paths": ["controls.knowledge.index"]},
    {"block": "control.knowledge_constraints", "when_paths": ["controls.knowledge.constraints"]}
  ]
}
```

`requires` 只补理解这些字段所需的定义；同一块在一次请求中只出现一次。格式由最终 schema 生成，正文不复制 required、enum 或每种嵌套。`maxItems=0` 等关闭列表仅显示空格式，不加载用途教学。

## 负责位置

| 修改内容 | 负责位置 |
|---|---|
| 全局角色、范围 | `共享/探索角色.prompt`、`run_context.py`；范围来自运行清单 |
| 本步目的 | 对应 `调用/*.prompt` |
| 字段含义与正例 | `对象/*.prompt` 中被 recipe 选中的稳定块 |
| 组合、条件、顺序 | `流程/调用组成.json::calls.<role>.field_sections` |
| 依赖、去重、局部格式 | `field_sections.py`、`object_blocks.py` |
| 平台合同、普通/专用纠错 | `output.py`；仅变呈现，不改输出能力 |
| 类型、枚举、必填与业务限制 | 实际 builder、校验与登记模块；基础 `.schema` 不一定是最终合同 |
| 条件追加字段 | `task_prerequisites.augment`、`discovery_completion.extend_schema`、`function_updates.attach` 等原生产入口 |
| 任务提出/结果复核 | `task_proposer.py`、`task_result_review.py`、`records/task_updates.py`；复核是单对象，更新是列表 |
| 功能登记 | `region_functions.request_schema`，不是旧静态“区块功能登记.schema” |
| user 中事实与历史 | 原 builder、`records/` 和 `compose.py` |
| 纠错诊断说明 | `correction_prompts.py` 与本轮选择的 `纠错/*.prompt`；字段规则已在 record_edit 等语义块维护 |
| 工作台配置来源 | `compose.configuration_paths`、`object_blocks.purpose`；使用当前调用身份，继续复用现有工作台 |

任务问题保存在 `tasks`；`operations` 是任务提出的历史输出名。不要以 prompt 重构改掉存储或调度协议。保留 `task.type`，业务目标仍通过 `object_blocks.task_definition` 读取它。

## 纠错与旧请求

原格式重答保持当时已发送的字段、文案及材料；不会自动换成本版新模板。普通纠错保留原调用说明，另外呈现本次 resolution、proposal、record_edit。完整 proposal 与局部顶层修订有不同说明；局部模式复用原字段格式，仅说明哪些顶层字段被替换。原字段定义改变时不会错误折叠为同一个合同。

记录字段按实际开放变体加载；无记录编辑能力时隐藏对应教学。共享关系调用虽然外层 role 是 step_correction，仍有自己的专用字段，不继承普通修订能力。

## 验证与本批边界

运行 `PYTHONPATH=src:tests python3 -m unittest -v test_prompt_composition test_exploration_purpose` 做 19 项聚焦检查（需正常 builder 的 Python 导入依赖）。40 个离线场景覆盖全部调用及必要变体；通过正式准备入口输出完整 system/user，不能将此视为 Luna 理解或真实遍历成功。

原生验收仍需从真实 run 经原 builder 构造完整上下文，使用原图调用 Luna，让原答经过原校验、纠错、登记及后读。本仓库已有这些资料和环境；本次仅完成两份真实记录的离线预览，0 新 Luna、0 GUI，尚未部署到原冻结运行。

## 新增任务类型的接入位置

当前类型为function、parameter、region_content。新增或改类型时同步：`对象/任务.prompt`目标、`object_blocks.task_definition`标签、`task_proposer.proposal_schema`与静态schema、`task_settlement.registration_kind/missing_product_fields`、`work_context.describe`及`history_disclosure.VALUES`展示。理由由`region_tasks.apply_plan`保存，`exploration_goal`与`history_context.action_context`提供给后续调用。region_content仅绑定区块，reason必填；沿原任务/动作链，不新增滚动次数或独立完成清单。

所有角色（含特殊纠错、恢复）的回复解析和schema错误共用 `纠错/原格式重答.prompt`，逻辑在 `runtime/reply_correction.py`，发送入口 `ModelTransport.call`。schema保持这一次实际调用的格式，不回退到更早探索步骤，不为错误字段生成第二套schema。错误展示在 `correction_feedback.py`，业务身份读回在 `records/calls.business_request`。
