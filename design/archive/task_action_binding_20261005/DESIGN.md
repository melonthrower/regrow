# 任务绑定动作与探索进度
设计基准：私有regrow已导出提交 dc2e46e900536a1360e12f3c80de817417cb19e3。当前候选不包含工作树原有地图/滚动修改；最终源码提交及核实行号另见审阅包 CHANGE_MAP.md。

## 问题与改动
原任务已有control/action，完成却依赖Luna的task_result.status；同一入口改任务名还能重复安排。现在同一区块按控件身份+动作复用，第三步用真实执行和登记观察更新“已探索”，不再另发普通完成判断。

| 位置 | 实现 |
|---|---|
| region_tasks.apply_plan | 同绑定沿用旧任务及状态、前置条件、历史；不同绑定才新建 |
| task_settlement | 集中维护绑定、可选后续绑定、动作匹配、进度和参数事实 |
| register_update.commit_update | 先附实际operation及文字发送记录，再匹配任务，在同一快照发布 |
| run_task_step / task_selection | 任务卡读当前绑定；已有可靠同绑定动作直接复用，不发累计结果核对 |
| update_step / 三步prompt | 普通任务更新只有task_update.findings与可空next_action；不再输出done/pending |
| suspended_updates | 原历史登记保留时点，相关区块有变化不覆盖，当前场景重新观察 |

## 必须保留的区别
- 已探索不等于业务成功。未变化、系统提示、局部内容均如实保存，不为了完成标签反复点击。
- 其他控件/动作、未确认关联、只有输入聚焦、缺真实观察都不能完成原绑定。
- 原绑定经新观察证明不合适时，可改next_action；保留原绑定及尝试，修正前旧动作不自动消费新绑定。
- 前置准备仍由本次条件观察结束；异常退出仍暂挂，不因恢复应用就重试。
- 同区块去重不承担跨区块语义目标合并；record/blocked不因改名变成explore。
- 保留显式归属修订与异常复查。旧未登记请求保留原答，只读其参数事实，不用旧模型status产生新进度。
- 采集和指令生成保持原合同：必须验证实际条件与业务结果，不能把遍历done当成功轨迹。

## 小量验收
1. 正常样式入口：实际展开两项，入口已探索，参数事实及图片归属正确。
2. 系统提示：入口点击已探索，真实异常与恢复交接保留。
3. 输入未送达：只记录聚焦，输入/准备仍未完成，不重放GUI补账。
4. 完整任务清点、动作选择请求：单图，已有同绑定不新增，普通完成复核字段消失。
5. 单元与相邻合同：错控件/动作、改绑、前置准备、异常退出、历史与归档恢复。

实现与验证分开：代码及90项聚焦检查完成，最终提示再检18项；5例原生保存帧Luna共5HTTP/0GUI，回复原样登记并核对任务/身份/图片。独立阅读与接受边界见本月日志及审阅包。没有新GUI或全应用遍历结论。

验证边界补充：partial_input原生例是prepares准备任务，原action为click；它证明未发送文字被如实记录、准备及主任务未误完成。普通input_text探索任务的自动结算只做离线验证；跨区改绑也仅离线验证。
