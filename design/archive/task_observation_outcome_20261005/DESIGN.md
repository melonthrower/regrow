# 任务提出的互斥结果：候选设计

状态：仅设计，未实现、未做Luna或GUI验收。用户希望减少不断补“不同状态组合”的分支。建议先用于任务提出；三步主流程及现行模块合同保持，采用前须完成下述原生验证。

## 改变回复的用途，复用原步骤

任务提出的一次回复只选一种用途：

| 用途 | Luna提供 | 框架处理 |
|---|---|---|
| 提交本步结果 | 原任务清点结果与任务增量 | 沿原校验和登记；inventory只用于这份任务结果。 |
| 请求补观察 | 当前区块内需要看清的问题，一句话 | 不携带任务提案，不写task_inventory或任务增量；原任务步骤保持pending，转已有补观察，再刷新同一请求。 |

这是互斥协议的语义要求，不是已实现JSON schema。实现时普通请求与纠错共用用途解析/校验入口，拒绝同时提交两种用途，不靠搜索evidence里的“没看见”决定分支。首批仅承诺区块级补观察：框架沿原请求绑定区块和来源帧，问题可以引用已披露控件名，但不产生required_control或特定控件已缺失的结论。现有discovery_step.focus_task只从task_name绑定控件，任务提出没有task_name，不能宣称已有控件级定位。完整性和模型依据仍须通过原语义检查。

纠错仍使用已有外层resolution：observe提出补观察；revise.proposal只允许正常任务结果，不嵌套第二个观察分支。归一化后的观察分支不得携带record_edit或任何任务修改；正常revise保留原有经校验的记录修订能力。这样同一种用途只有一个纠错入口。

这样“任务已列齐，但当前控件记录不可信”应选择补观察，回复中不再出现complete或新任务。正常结果中原有partial/uncertain及滚动补齐仍沿现行规则，本提案不消除所有旧状态；它避免新增地图疑问状态再与inventory交叉。框架可以拒绝结构上混填，但模型未意识到冲突或误选正常结果仍可能出错。

## 为什么不用再保存另一套待办

现有step_repair.Runner已经在调用前保存原步骤，observe分支保存observation_question；repair_stages.observe_registered通过子发现步骤登记补观察，随后refresh原请求。拟在正常任务回复中提前开放该出口，而不是先提交任务清点、结束原步骤，再另建待核对列表和重新清点义务。

正常补观察请求需在任务语义登记前分流；只进入已有父episode，保留其请求、次数、补观察结果和恢复指针。观察登记并确认原区块仍适用后，刷新同一任务请求再让Luna选择回复用途。当前Runner补观察后对task_proposal仍回repair，需明确调整这条“主动补观察”返回路径，不能只加schema后声称自然续进已接通。原校验失败的纠错路径继续保留自己的语义。

恢复也不能直接视为已有保证。observe_registered目前先增加父观察次数、后创建子episode；子步骤完成后再记父supplements，两处之间的进程中断会留下接力空隙。采用前须在现有父子episode中保存并复用明确的子步骤引用，用它判断待启动、待续接或结果待接收；已有次数只记账，不单凭次数拒绝续接。覆盖这两处直接相关的恢复窗口，不扩展为新的业务状态清单。正常pending的额度暂停及上述进程恢复应继续原步骤；blocked后经既有重新进入路径触发重开（不新增人工审批），仍允许reopen_blocked保留旧episode审计并另开观察，不承诺同一episode、不改该生命周期。下文“显式重开”均指这条代码路径。

请求能力按阶段及证据来源限定：历史清点不得请求实时截图；已执行动作的结算不得用新观察替代原后图。第一步的主动补观察不执行GUI业务操作。原区块不再适用或同一步骤补观察仍不能解决时，沿已有暂停/暂挂边界保留工作，不重开无限核对。

遮挡但能认出对象且不影响当前任务时继续正常结果；模板资格独立，不把每个缺图都变成补观察。

## 拟改位置和范围

| 位置 | 已有机制 / 拟修改 |
|---|---|
| region_tasks.proposal_schema / plan_request、区块探索任务.schema及任务提示 | 已有清点输出；拟提供互斥的提交/补观察出口。普通、刷新、历史请求的能力需同步。 |
| step_repair.Runner.perform / request | 已有pending、observe、次数与纠错；拟在正常任务回复接纳前统一分流，明确主动补观察后的原步骤重提。纠错schema须避免将包装后的回复再重复包装。 |
| repair_stages.accept_candidate / observe_registered / refresh；discovery_step.focus_task | 复用区块级观察与刷新，不假定绑定某个控件。补齐父子episode交接引用及上述两个恢复窗口；仅正常结果进入任务语义校验，观察请求先校验格式、来源与能力。 |
| step_repair.submission、region_tasks.commit_plan / apply_plan、registration_diagnostics.collect | 统一取出实际任务结果，保留原请求/原答；登记与诊断不能各自猜回复格式。检查所有直接读取reply的路径。 |
| run_task_step._run_step / task_selection.attach；step_repair.reopen_blocked | 核对pending优先续接；原步骤完成或明确暂挂后才进入普通调度。不新增调度标记，blocked显式重开仍保留既有取代关系。 |
| 三步与纠错的生成prompt | 核对共用包装、图片数量、阶段能力和事实时点；首批只改任务提出协议，动作/更新不声称已迁移为统一输出。 |

没有新增框架文件的必要。共享分流放在既有Runner/适配入口；不建立新工作流引擎，不改视觉匹配与图模板门槛。

与旧map_task_repair_20261005草案的关系：这是对其“control_issues + control_review + awaiting_task_plan”交接部分的候选简化，尚未决定整体替换。旧草案中的地图当前/历史区分、错误记录核对及任务复用问题仍需处理；本提案只降低交接状态组合，不宣称解决任务防重或当前地图全部错误。

此出口只在任务提出已被调用时生效；inventory已经complete而调度不再提出任务时，它不会自动发起核对。何时因新的画面变化重新清点，仍属于调度与当前证据的独立职责。

## 用少数规则验收

1. 提交结果才会写任务。任何补观察请求（含格式混填反例）都不能顺带登记任务、前置条件或完成状态。
2. 补观察后仍继续原步骤：验证额度暂停及上文两个交接窗口的进程恢复，刷新原区块和证据；原区块变化时不把任务挪给另一页，已有GUI不得重发。blocked显式重开另验已有审计取代关系，不混同正常续接。同区块多个控件时，问题中提到其中一个也只请求区块级核对，不据此伪造控件绑定或缺失结论。
3. 同一未解决问题遵守已有观察/纠错上限；局部遮挡正例能够直接提交正常结果，不引入固定额外调用。

先以真实旧失败run经正常任务入口生成完整请求；原Luna回复不改，走正常Runner观察/登记/刷新，再检查实际身份、当前清单、任务与图片。普通结果、主动补观察、暂停后恢复和仍未解决为直接验收范围；历史材料能力边界及混填拒绝用必要相邻检查。测试可以有少量代表组合，但程序只依赖统一分流与这些规则。

本轮仅完成设计与代码位置核对。是否采用及具体输出字段需结合代表性Luna调用确认；没有新GUI或行为改善结论。
