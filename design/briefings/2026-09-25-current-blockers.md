2026-09-25 · 给学长的阶段汇报 · v1

**目前已经能在真实界面上探索、操作并积累功能图，但还没有证明：它能以可接受的成本，持续、可靠地完成探索，并支撑后续复杂任务轨迹的批量构造。最近最直接的阻塞，是“已经识别出当前页面，却仍无法转入下一步动作”。**

## 1. 我们要做什么，现在卡在哪一段

目标链条：**真实界面探索 → 可复用的功能图 → 生成有实际意义的任务 → 实机执行并验证最终结果 → 训练数据。**

这里的 Region 指功能区块，例如时钟应用的公共导航栏、闹钟内容区、搜索对话框。我们希望记住区块及控件的身份、功能、参数和进入关系，减少重复探索，再利用这些知识构造任务。

现在主要卡在第一段到第二段的稳定闭环：识别、动作、更新、任务调度单独可以工作，但串起来后会出现身份污染、重复整理、导航停滞和覆盖不均衡。后续任务生成与采集已有局部试点，不能因此说整条方法链已验收。以下用近期桌面 Clock 的真实记录说明，不把单应用案例推广为所有应用的总体结论。

旧运行的0077更新却把新输入框接到旧按钮身份c0028；随后原按钮又被登记成新身份c0035。结果是**按钮与输入框的图片、名称、动作历史混在一起**。这样即使图看起来连通，后续复用也可能找错对象。

正确规则应区分三件事：原控件移动、原控件状态变化（Start变Pause）、新控件出现。不能只因“都是搜索相关”就继承同一身份。

**修复状态：已有局部修复。** 后续正常框架保存帧验证用2次真实模型调用、0次新GUI动作，确认搜索按钮保留身份、新输入框独立登记，Start变Pause也保留原身份。这支持局部修复，不证明历史污染图已修好，也不证明连续探索再无身份错误。修复与验证说明（见本地图文包）

## 4. 效率问题：很多调用用在整理和回访，功能覆盖仍不均衡

一轮已完成审计的独立旧运行，从空图开始，消耗 **96次模型调用、31次计费GUI命令**，累计模型等待约 **46.7分钟**，最后因额度预留停止。时间是各次请求等待之和，不是完整墙钟耗时；GUI命令包括恢复与导航，不等于成功探索的控件数。

| 调用用途 | 次数 |
|---|---:|
| 动作选择 / 动作后更新 | 28 / 27 |
| 功能登记 / 任务生成 | 17 / 11 |
| 界面发现 | 7 |
| 步骤纠错 / 异常恢复 / 累计结果核对 | 3 / 2 / 1 |

具体表现：公共导航栏功能登记6次、应用菜单3次；Shortcuts已有待办后先离开，后来再返回。期间也探索了About、Credits、Timer，不能把整个回访区间都算浪费，更不能简单删掉所有观察和纠错。

该旧运行结束时有11个区块、35个控件身份，但World和Alarms还没有任务清单。**“没有pending任务”可能只是“尚未生成待办”，并不表示已经探索完。** 最新续跑已进入新建闹钟对话框，因此这里是旧运行的覆盖不均衡证据，不是说当前从未探索Alarms。

需要解决：哪些新增证据值得重新总结功能？怎样在保留原工作区闭环的同时减少无意义回访？怎样把未清点区块纳入完成判断？目前只有单轮成本描述，尚无同等功能覆盖下的前后成本对照。旧运行统计（见本地图文包）

## 6. 希望和学长讨论的三个问题

1. **探索边界怎么定？** 对明确常识效果直接登记，把动作预算留给未知页面、有限选项与条件关系；哪些功能仍必须实际执行，才能支撑后续任务构造？
2. **如何证明功能图值得引入？** 在同一组人工核对的功能覆盖下，比较模型调用、GUI动作、耗时和身份错误，而不是只比较图节点多不多；目前还缺这样的对照证据。
3. **最小的端到端成果是什么？** 建议先选少量可验证的真实业务目标，贯通“图→指令→实机完成→结果证据”，同时把导航子轨迹、人工干预、失败和清理步骤分开统计，再决定何时扩大应用规模。

近期优先顺序建议：**先解决当前识别→导航停滞，再验证身份及任务账本一致性，然后做同覆盖成本对照，最后扩大复杂任务采集。** 这是讨论建议，不是已执行的新设计或已通过的实验结果。
