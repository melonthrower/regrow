# 待解决方向：纯视觉(VLM)功能提取 —— 遍历时边滚边提，不依赖 a11y

日期：2026-06-17
状态：**方向已提出，未实现**（当前用"a11y 辅助屏下"的折中方案，见 design_decisions D24）
关联：D24（视觉优先 capability 合成）、D18/D20（移动端滚动聚合）、D11（发现型 SCROLL）

## 背景：当前方案是"a11y 辅助屏下"

D24 把 capability 合成改成**视觉优先**：VLM 看单张截图判断"活跃表面 + 本页特有功能 +
排除导航/chrome"。但单张截图只有首屏(y≤屏高)，滚动线以下的真功能控件拍不到。

折中补救（已实现）：屏下部分靠 **a11y 元素清单**(elements.json，GTK 暴露 viewport 外
元素带真实坐标)补回——给 `screen_y ≥ 屏高` 的元素标 `[屏幕下方-需滚动才可见]`，prompt
让 VLM 也提取它们。

**这仍然依赖 a11y**：屏下功能能不能提取，取决于 a11y 有没有暴露那些元素。在 a11y 不可靠
的平台/控件上（GTK combo 不暴露、移动端某些自绘控件、a11y 服务降级等），屏下功能照样漏。

## 纯 VLM 方案：遍历时就提取功能

**核心思路**：遍历本来就会滚动浏览整页(D18/D20 滚动聚合)。在那个过程里，**每滚一屏都有
一张真实截图**。与其事后用单帧截图 + a11y 补屏下，不如在遍历滚动时**边滚边让 VLM 看每屏
截图提取功能**，把多屏结果合并去重 → 完全不依赖 a11y，屏下功能因为"滚到了就拍到了"而被
自然看到。

优点：
- 彻底摆脱 a11y 依赖（项目"视觉主导"大方向，见 MEMORY vlm-visual-grounding-plan）。
- 屏下功能不再靠 a11y 暴露，靠滚动截图覆盖。
- 与遍历的滚动聚合天然契合（滚动动作已有，只是没在那时调 VLM 提功能）。

待解决的设计问题：
1. **触发时机**：在 `_android_scroll_aggregate_elements` / 桌面滚动发现的每次滚动后，
   对当前屏截图调一次 capability 提取？还是滚完收集所有屏截图再一次性多图喂 VLM？
   （前者调用多但每屏聚焦；后者一次调用但多图 token 大。）
2. **多屏去重合并**：同一功能在相邻两屏都可见(滚动有重叠)→ 需按功能名/视觉位置去重。
   类似 D18 元素聚合的"连续 patience 次无新增"思路。
3. **接地**：纯视觉提取的功能没有 a11y id → 实机执行靠坐标点击(已在 D24 _filter_hallucinated
   保留无 id 功能 + 执行 prompt 支持 x/y 坐标动作)。需验证坐标接地的稳定性。
4. **成本**：遍历每个节点多次 VLM 调用，token/时间成本上升。是否只对"长页"(滚动聚合
   发现 viewport 外元素的节点)启用。
5. **与现有合成的关系**：是替换 capability_synthesizer 的单帧合成，还是作为"长页"的补充
   路径？建议先并存：短页用单帧视觉(D24)，长页用遍历多屏。

## 现状小结

- 短页(首屏装得下)：D24 单帧视觉已经干净准确(导航排除、参数化归并、活跃表面)。
- 长页：D24 + a11y 屏下补全可用，但依赖 a11y。纯 VLM 多屏方案是 a11y 不可靠时的治本路线。

接续点：在遍历滚动聚合处插入"每屏截图 → VLM 提功能 → 多屏去重合并"，先在一个长页节点
(如 Multitasking / VS Code Extensions)上原型验证，对比 a11y 辅助方案的覆盖与准确度。
