## 1. Pipeline 与职责

设计主循环：发现与登记 → 动作 → 观察与更新 → 动作；应用外异常 → 恢复确认 → 发现与登记 → 动作。恢复确认只判断目标应用前景，清空旧可交互落点并保留工作区块，禁止直接跳过发现进入动作。

- Luna：视觉识别、动作建议、结果及知识增量提议；不承担持久ID分配或预算计数。
- 程序：组织输入、分配/关联记录、投递、持久化及根据已接受状态选择下一动作模式。
- 动作选择与程序执行是一个动作步的内部环节；不额外调用模型批准其自己的建议。人工停在建议后只属本次调试停点。
- 更新必须完成校验和登记后才能交接下一动作；模型回复落盘不等于更新已提交。

**已实现部分**：stepwise_flow.py 有 observe/choose/execute/settle 顺序驱动、请求组装和后台关联。**已接通登记入口**：register_update.commit_update将已校验结果持久化并发布运行交接。普通探索的统一实机循环仍未完成；异常恢复已有独立可执行入口recover_external.py，恢复后暂停。不能因函数已有阶段名就称闭环已接通。

## 2. Region 知识与物理存储

### 2.1 一区块一份 JSON（本次已实现登记）

```text
run/
├── knowledge_current.json       # 当前已完整提交的快照入口
├── knowledge_snapshots/<更新>/
│   ├── regions/r0001/region.json # 内嵌控件、动作、关系、探索、历史
│   ├── regions/r0001/images/     # 本次新增/变化的视觉裁剪
│   └── runtime_state.json       # 工作区块、当前区块、下一分支
├── action_attempts/              # 实际动作回执和前后图
├── calls/                        # 原始请求/回复
└── graph_snapshots/              # 原探索证据，不覆盖
```

region.json 内嵌 name、description、observations、controls、functions、actions、transitions、reached_by；不为每个紧密关联的小对象再建一份JSON。内部ID只用于关联，文件路径相对其所在JSON。图片与原始执行证据另存，引用不复制整份目标Region。

- 控件属于Region，保存文字/图标外观及各观察时的状态和图像；外观变化不覆盖旧观察。
- 功能属于Region，通过ID关联可能参与的多个控件和动作证据；功能不等于一个按钮。
- 动作归来源Region，可影响多个Region。实际证据只有一份；不能从返回索引虚构已走过的反向边。
- 当前可见/可操作状态与持久区块知识分开；不可见不删除控件或功能。
- 入口尝试、功能验证、目标区块探索、整区完成是不同含义。

**当前读取入口**为knowledge_current.json指向的完整快照，首次从旧图导入已有区块/控件/动作；后续在当前记录上更新。图片路径相对所在region.json，旧图片直接引用，新可靠框生成裁剪。所有原始证据及旧region_records保留。动作按attempt编号唯一存储，控件action_refs可直接检索效果；同一次动作的新评估保留历史版本，不新增点击。functions当前为空，不编造尚未登记的功能。

### 2.2 统一登记字段与编号

- 区块名称、描述直接放顶层；控件以内部ID为字典键，内部只有name、observations、action_refs，不再重复id/owner或包一层proposal。
- observations逐次保存当时文字、图标外观、状态、图像及evidence来源，不保存bbox/icon_bbox。原始识别框仅供当轮裁剪，继续保留在原始调用证据中。当前可交互清单放runtime_state，不把旧“可见”描述当当前状态。更新已知控件追加观察，名称变化保留身份和动作引用。
- actions以实际attempt为键；control、operation、purpose、delivery、result、region_changes、interactive_regions与evidence归同一条动作。新评估整组替换结果及区块变化，旧评估保留在不可变快照；不把旧变化标上新调用来源。
- 不再保存区块顶层history/exploration。控件尝试情况从action_refs和actions按需计算；无尝试记录与结果未确认分开，不持久列remaining_controls，不判断整区完成。动作的region_changes保留一次当前采用的评估；not_visible仅表示动作后图未见该区块，不表示删除或探索完成。functions无证据时保持空。
- 内部ID不具有决策含义，只保持改名/同名时引用稳定。名称用于阅读和模型回答；同名不自动合并，动作按名称与位置唯一关联，更新的纯名称映射有歧义就拒绝，不猜对象。观察编号仅属于证据引用。
- commit_discovery将已有发现证据登记为上述结构；commit_update在同一结构上更新。旧格式实验显式从保存图重建一次，新快照不会被旧发现覆盖。原region_records只作历史，不再作为当前读取入口。

## 4. 发现与识别步（含登记）

### 4.1 当前入口与已有证据

**当前入口**：discovery_step.request_from_run / run_stage，接收运行状态及当前帧，由程序视觉匹配决定局部定位或区块重定位；复用通用前景、分区与裁剪规则，任务prompt按两种范围分开。assemble.py保留首次实验输入的历史来源，当前恢复不再走先枚举全屏控件再文字召回的路径。

### 4.2 工作区块优先，失去位置时扩大识别（已实现，保存帧验证）

2026-09-20当前实现：发现阶段主要识别区块，不要求Luna一次输出整屏全部控件。先定位当前工作区块及其局部控件；不能可靠定位时，才扩大到当前画面的区块。这里“页面”仅指当前截图，不引入Page身份。已替换固定的“整屏控件发现→文字候选复核”两调用路径；一次局部定位可直接登记，扩大重定位后再按需核对局部控件。

**模式一：工作区块局部定位。** 输入当前截图、保留的working_region、该区块的历史代表图/控件图和本轮任务。程序先匹配区块外观、少量有区分力的控件锚点及组合布局；定位后，只在该区块范围内核对当前任务需要的控件。不要每轮匹配全应用控件，也不要求所有旧控件同时命中才认为区块存在。滚动、状态变化、遮挡和相似图标可能导致漏匹配；单个图标命中也不能证明整个区块身份或可交互性。匹配结果作为发现prompt的候选证据，由观察确认或纠正。

**模式二：当前画面的区块重定位。** 没有已知工作区块（首次进入）、已确认工作区块不在当前可交互表面，或局部定位仍不确定时进入。程序扩大检索已有区块的代表图与精简控件锚点，召回当前画面的区块候选；Luna确认当前区块组成并补充未命中的新区块。全面指覆盖当前画面的区块，不是遍历整个应用的所有控件模板。无匹配不能直接登记为新区块；未确定落点时不计算可执行返回路线。

工作区块的定位结论应区分“已确认可交互”“当前不可交互/未显示”“尚不能确定”。程序未匹配到只是证据不足，不直接等于区块不存在。已知区块只有少量控件变化时优先局部补充，不自动升级为全屏重发现。

**落点与任务分开。** 重定位只更新当前可交互区块集合，不改变未完成的working_region。落点确认后，从当前区块沿已记录正向动作关系计算前往工作区块的最短已知路径；没有路径就保留任务与缺口，不猜反向边。导航时只定位下一步实际要操作的控件；执行一步后走更新步核对落点，进入原区块后恢复模式一。

**区块与控件分层披露。** 全屏发现只输出区块描述、范围、身份/可交互判断及必要定位锚点，不递归展开每个区块的全部控件。选定工作区块后，再识别、比对和增量登记区块内控件。桌面上的大型区块仍可按可见范围和本轮子任务分批处理；保留未检查范围，不把单轮输出结束、空列表或输出截断视为清点完成。未检查、当前未显示、确实不存在必须分开。

**模块交接。** 程序视觉匹配输出候选及匹配证据；发现prompt输出确认的区块/局部控件与不确定事项；登记模块更新现有记录；路径模块读取确认落点与原任务。两种模式属于同一发现与识别步的不同输入范围，共用匹配和登记能力，不各自维护一套知识。

**耗时与验证边界。** 全控件模板逐一匹配的成本会随模板数量增长，不设为每轮默认操作。已有Clock试验12模板约4.18秒、7个可见控件均命中、5个不可见菜单项均拒绝，仅是单帧证据，不能外推桌面大库的准确率或耗时。后续需验证局部定位能否少查模板、错误定位能否触发重定位，以及桌面大量控件时是否只披露区块和必要控件；本轮73项聚焦离线测试通过，新增2次Luna保存帧调用、0GUI。call0012只登记主体区块、controls为空；call0013只登记菜单按钮，原菜单任务保留，后续动作请求可生成。原导航区块仍保留，但0012未单独列为当前区块，不据此声称整屏识别完整。详见records/022_local_region_discovery_20260920_01。

## 6. 更新步

### 6.1 当前prompt与输出

**已实现普通动作的组装与登记；恢复后改接发现步**：[update_step.py](update_step.py)的build_update_request读取[03结果/更新清单](遍历prompt/流程/03_结果核对.json)，复用识别规则和[更新固定片段](遍历prompt/更新/动作后观察与状态更新.prompt)。本轮输出使用[动作后更新.schema](遍历prompt/输出格式/动作后更新.schema)，旧call快照不改写。

输入：目标应用、此前工作区块与局部历史、实际动作、回执、前后图。输出：观察结果、区块/控件变化、工作上下文、探索更新与交接摘要。更新步不建议下一动作。

动作结果统一为：

```json
{
  "action_result": {
    "exception": "external_app",
    "description": "点击 Privacy policy 后显示 Chrome 欢迎页；未看到隐私政策正文。",
    "evidence": "动作前为 Clock 菜单，动作后为 Welcome to Chrome。"
  }
}
```

不再单独输出current_context.scope/kind、goal_status或重复的可见结果status。实际变化和仍未确认的内容写description，依据写evidence；执行是否投递仍读取程序回执。没有功能验收条件时不让模型再猜一个“目标是否完成”的枚举。

异常枚举的当前边界：

| exception | 含义 | 不意味着 |
|---|---|---|
| none | 未观察到已定义异常 | 动作成功、功能完成、区块完成 |
| external_app | 动作后进入目标应用外 | 功能失败或隐私政策已显示 |
| uncertain | 证据不足，无法确定异常情况 | 可以当作none继续操作 |

没有可见变化先写事实，不自动增加异常类型；系统界面不全部当external_app，不能判断时写uncertain。混合窗口、其他异常和恢复策略按真实案例补充，不宣称三值覆盖所有场景。

### 6.2 如果发现到了应用外了，框架如何处理、登记？

来源Region保留本次动作，result引用上述exception/description/evidence；不创建Chrome作为Clock节点，不伪造内部跳转边。例：

```json
{
  "controls": {
    "c0010": {"name": "Privacy policy", "action_refs": ["a0002"]}
  },
  "actions": {
    "a0002": {
      "control": "c0010",
      "operation": "tap",
      "delivery": "executed_receipt_zero",
      "result": {
        "exception": "external_app",
        "description": "出现 Chrome 欢迎页，隐私政策正文未确认。",
        "evidence": "本次动作前后截图"
      },
      "interactive_regions": [],
      "evidence": {"result_call": "0008"}
    }
  },
  "transitions": []
}
```

这是简化示意；实际新快照已按一个Region一份JSON组织。运行状态保留工作Region和最后已接受更新的引用，从对应action_result读取异常，不再另存一份同义scope判断。当前可见目标区块可为空，历史工作区块及控件仍保留；4个无尝试记录的入口由程序即时计算。首次发现没有动作，不制造action_result。

### 6.3 校验与提交边界

**已实现** route_update：schema校验、确认执行回执、模型尝试状态与回执一致、纯外部前景不能同时登记目标应用当前区块。格式无效抛出具体错误，不补默认none；回执未确认进入程序执行核对，不让模型的external_app掩盖投递问题。程序检查不保证所有视觉判断正确。

**已实现** register_update.commit_update：按真实动作来源关联控件，名称必须唯一对应；登记效果和区块变化，计算控件action_refs与区块探索进度，不保存整体完成提议。新/变化的应用内区块与控件登记为候选；产生目标的观察候选边，目标仅存到达索引，不推导反向可执行边。对未变的同屏背景不另建跳转。应用外结果保存在动作中，不建应用内目标节点。

全部文件先写入本次临时目录，完成后发布不可变快照并替换当前指针。写入失败不把半成品交给动作步；发布指针中断可重试。重复相同提交不改内容，旧提交重放不回滚新入口。此为串行实验写入，不是并发数据库。原始证据不覆盖。

## 7. 更新后的异常检测与分派

### 7.1 检测与分支候选（已实现）

程序读取action_result.exception，不搜索“Chrome”等关键词、不凭regions为空猜应用外。分支规则在update_step.route_update：

| 情况 | next_action_mode | 处理边界 |
|---|---|---|
| 更新格式/字段矛盾 | 不产生有效候选 | 留在更新纠正 |
| 实际回执未确认执行 | review_execution | 保留程序执行问题，不擅自重投 |
| external_app | recover_scope | 保留工作区，下一动作目标为恢复 |
| uncertain | review_result | 补充观察核对，不自动Back |
| none且有目标应用区块 | explore | 可进入普通动作决策，不等于完成 |
| none但没有可用目标区块 | review_result | 空清单不是完成或可执行证据 |

输出例：

```json
{
  "status": "validated_candidate",
  "next_action_mode": "recover_scope",
  "reason": "external_app"
}
```
