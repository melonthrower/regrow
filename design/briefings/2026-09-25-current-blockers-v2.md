# GUI-ReWalk：当前卡点与需要解决的问题

2026-09-25 · 给学长的阶段汇报 · v2

**目前已经能在真实界面上探索、操作并积累功能图，但还没有证明：它能以可接受的成本，持续、可靠地完成探索，并支撑后续复杂任务轨迹的批量构造。最近最直接的阻塞，是“已经识别出当前页面，却仍无法转入下一步动作”。**

## 1. 我们要做什么，现在卡在哪一段

目标链条：**真实界面探索 → 可复用的功能图 → 生成有实际意义的任务 → 实机执行并验证最终结果 → 训练数据。**

这里的 Region 指功能区块，例如时钟应用的公共导航栏、闹钟内容区、搜索对话框。我们希望记住区块及控件的身份、功能、参数和进入关系，减少重复探索，再利用这些知识构造任务。

现在主要卡在第一段到第二段的稳定闭环：识别、动作、更新、任务调度单独可以工作，但串起来后会出现身份污染、重复整理、导航停滞和覆盖不均衡。后续任务生成与采集已有局部试点，不能因此说整条方法链已验收。以下用近期桌面 Clock 的真实记录说明，不把单应用案例推广为所有应用的总体结论。

## 2. 框架怎样工作：三段探索，加调度与异常处理

下面介绍近期实验使用的 **Region逐步遍历器**。它围绕一个工作区块推进，视觉模型Luna负责理解截图、提出动作和解释结果；程序负责身份关联、动作投递、校验登记、调度和预算。模型说“完成”后仍需经过正常登记，不能把一句回复直接当成图中的事实。

### 三段探索分别做什么

**① 发现与识别 → ② 选择并执行动作 → ③ 观察结果与更新知识。**

| 阶段 | 回答什么问题 | 主要输入与产出 |
|---|---|---|
| ① 发现与识别 | 现在在哪里？哪些区块和控件真正可交互？是否见过？ | 根据当前截图与相关历史，识别前景、区块和控件，登记身份与图像证据；优先局部识别，位置不确定时扩大到当前画面的区块 |
| ② 选择并执行动作 | 为当前探索任务，下一步做什么？ | Luna根据目标、当前图和已有尝试提出一步动作；程序核对目标绑定及投递前画面，再执行并保存回执、前后截图 |
| ③ 观察结果与更新 | 实际发生了什么？任务推进了吗？知识有哪些变化？ | 结合真实前后图、回执和任务历史，判断结果，更新控件状态/身份、区块变化、任务发现与动作关系；校验登记后才交接下一步 |

**这不是每轮固定三次模型调用。** 已定位且上下文可靠时，②与③可以继续循环；进入未知界面、定位不足或恢复后，再回①。任务清点、功能整理、纠错也会带来额外调用。因此，前面说的“一次GUI动作”通常不等于“一次模型调用”。

### 中间还有一层任务与知识管理

发现控件后，先判断它的功能是否还存在值得探索的未知：已明确的常识功能可直接记录，未知页面、有限选项或条件关系形成探索任务；缺少前置条件的任务保留原因。功能整理把发现和任务结果汇总成区块能力，供后续任务构造使用，**仅记录功能不代表已经执行验证**。

程序同时保存三类东西：**功能图**（区块、控件、真实动作关系）、**任务账本**（待探索、已完成、受阻及原因）、**证据**（请求回复、前后图和回执）。它们需要互相一致，否则可能出现“图里有入口，却无法导航”或“待办空了，却还有区块未清点”。

“当前画面”与“工作区块”是两件事。例如，为探索菜单而打开一个子窗口，眼前是子窗口，原工作区仍可能是菜单。调度要保留原任务，再根据当前前景和已知关系决定继续、返回还是转入其他区块；不能看到新窗口就直接宣告旧区块完成。

### 异常处理不是一条“失败就重试”的分支

| 遇到的问题 | 框架的处理路径 | 保留的边界 |
|---|---|---|
| 界面异常：遮挡、进入外部应用、目标退出或无响应 | 进入恢复流程，根据当前截图选择恢复动作；确认恢复后回①重新识别 | 恢复成功不等于原业务任务成功；不直接沿用旧坐标继续点 |
| 识别/登记/动作绑定不合要求 | 进入步骤纠错，按具体错误补观察或修订；更新失败时保留已执行动作，继续处理其结果 | 不为了重试模型更新而重放GUI；格式通过不保证语义正确 |
| 局部任务受阻，或反复识别却没有进展 | 在有合适独立候选时暂挂并切换；没有可靠继续路径则保留断点暂停 | 暂挂不计完成；不能无条件跳过未结算动作或不可信前景 |
| 模型请求暂时失败 / 额度不足 | 请求按有限重试及独立记账处理；额度不足暂停 | 请求重试不等于GUI重试；额度由程序管理 |

这些路径已有实现和不同范围的局部证据，**不代表所有异常都能自动恢复**。后文最新案例正是：①反复得到识别结果，却没能交给②，随后进入分支纠错并停止。

### 用搜索框例子把三段串起来

后文图中的Shortcuts界面：**①识别左上角搜索按钮 → ②点击它 → ③确认输入框出现，同时原按钮仍在。** ③应该保留原按钮身份，并为新增输入框登记独立身份；接着按需补清点或继续任务。这里若把两者误认为同一个控件，错误会写进功能图并影响后续复用。

因此，后文的问题可以对应到三个位置：**识别→动作的交接停滞；结果更新中的身份错误；任务调度与功能整理的重复成本。** 需要修的是这些环节的实际协同，不能只看某一次模型回复是否合理。

图2b：点击后，中间新增输入框，左上角原按钮仍然存在，只是位置上移。两张都是旧运行的真实前后图，非本次新执行。

旧运行的0077更新却把新输入框接到旧按钮身份c0028；随后原按钮又被登记成新身份c0035。结果是**按钮与输入框的图片、名称、动作历史混在一起**。这样即使图看起来连通，后续复用也可能找错对象。

正确规则应区分三件事：原控件移动、原控件状态变化（Start变Pause）、新控件出现。不能只因“都是搜索相关”就继承同一身份。

**修复状态：已有局部修复。** 后续正常框架保存帧验证用2次真实模型调用、0次新GUI动作，确认搜索按钮保留身份、新输入框独立登记，Start变Pause也保留原身份。这支持局部修复，不证明历史污染图已修好，也不证明连续探索再无身份错误。修复与验证说明（见本地图文包）

## 5. 效率问题：很多调用用在整理和回访，功能覆盖仍不均衡

一轮已完成审计的独立旧运行，从空图开始，消耗 **96次模型调用、31次计费GUI命令**，累计模型等待约 **46.7分钟**，最后因额度预留停止。时间是各次请求等待之和，不是完整墙钟耗时；GUI命令包括恢复与导航，不等于成功探索的控件数。

| 调用用途 | 次数 |
|---|---:|
| 动作选择 / 动作后更新 | 28 / 27 |
| 功能登记 / 任务生成 | 17 / 11 |
| 界面发现 | 7 |
| 步骤纠错 / 异常恢复 / 累计结果核对 | 3 / 2 / 1 |
| 合计 | 96 |

具体表现：公共导航栏功能登记6次、应用菜单3次；Shortcuts已有待办后先离开，后来再返回。期间也探索了About、Credits、Timer，不能把整个回访区间都算浪费，更不能简单删掉所有观察和纠错。

该旧运行结束时有11个区块、35个控件身份，但World和Alarms还没有任务清单。**“没有pending任务”可能只是“尚未生成待办”，并不表示已经探索完。** 最新续跑已进入新建闹钟对话框，因此这里是旧运行的覆盖不均衡证据，不是说当前从未探索Alarms。

需要解决：哪些新增证据值得重新总结功能？怎样在保留原工作区闭环的同时减少无意义回访？怎样把未清点区块纳入完成判断？目前只有单轮成本描述，尚无同等功能覆盖下的前后成本对照。旧运行统计（见本地图文包）

这说明我们已有可以保留的局部能力，但还需要把修复放回正常上下文中验证连续推进。此前“前景接管优先”的补丁已被“原工作区闭环”方案取代，不应同时当作两项当前解决方案。

## 7. 希望和学长讨论的三个问题

1. **探索边界怎么定？** 对明确常识效果直接登记，把动作预算留给未知页面、有限选项与条件关系；哪些功能仍必须实际执行，才能支撑后续任务构造？
2. **如何证明功能图值得引入？** 在同一组人工核对的功能覆盖下，比较模型调用、GUI动作、耗时和身份错误，而不是只比较图节点多不多；目前还缺这样的对照证据。
3. **最小的端到端成果是什么？** 建议先选少量可验证的真实业务目标，贯通“图→指令→实机完成→结果证据”，同时把导航子轨迹、人工干预、失败和清理步骤分开统计，再决定何时扩大应用规模。

近期优先顺序建议：**先解决当前识别→导航停滞，再验证身份及任务账本一致性，然后做同覆盖成本对照，最后扩大复杂任务采集。** 这是讨论建议，不是已执行的新设计或已通过的实验结果。
