# GUI-ReWalk 框架图解：从一张界面到功能知识

2026-09-25 · v1 · 以近期实验的 Region 逐步遍历器为对象

本文用真实 Clock 截图解释框架主体、三段探索、回溯导航、异常处理和存储结构。**图片是已有运行证据，文字解释是本次整理；没有新增GUI操作，也没有宣称完整应用探索或任务采集已验收。**

## 1. 我们希望做什么

整体目标是：**探索真实应用 → 建立可复用的功能图 → 生成有意义的任务 → 实机执行并验证结果 → 收集训练轨迹。**

探索不只保存“点了哪里”，还要积累：应用能做什么、通过什么控件完成、有哪些参数和条件，以及如何到达对应界面。目前主要解决探索与功能知识积累的稳定性；下游已有局部试点，不代表整条方法链已经验证。

框架主体包含三个阶段，任务管理与异常处理贯穿其中：

```text
① 发现与识别：确认前景 → 识别区块 → 核对历史身份 → 识别局部控件
                      ↓
   任务与调度：判断值得探索的未知，保留目标和前置条件
                      ↓
② 动作阶段：必要时回溯/导航 → 选择一步操作 → 核对现场 → 执行
                      ↓
③ 结果与更新：观察真实变化 → 更新身份、任务和关系 → 整理功能知识
                      ↓
   位置可靠则继续动作；需重新理解现场则回①；异常时进入恢复/纠错
```

Luna负责理解截图、建议动作和解释结果；程序负责组织上下文、身份引用、执行、校验登记、调度和预算。三阶段不是每轮固定三次调用：局部识别、任务清点、功能整理与纠错都可能产生额外调用。

## 3. 第一阶段：发现与识别如何处理这些画面

### 3.1 先确认前景，再划分区块

对照图1与图2：图1中公共导航和Alarms内容都能参与操作；图2中则应以New Alarm为可交互前景。不能因为背景导航仍可见，就继续将其当作当前可点击入口。

分区依据是功能职责与交互上下文。例如，固定导航与可替换内容分开；New Alarm中的时间、名称和时长共同服务于新建闹钟。这不是每个按钮都建立一个Region，也不是整个应用窗口永远只有一个Region。

### 3.2 先局部定位，位置不明时再扩大观察

如果正在调查图3中的Ring Duration，优先定位New Alarm及相关控件。若区块不在当前前景或定位不足，则扩大到当前截图的区块，重新确认位置。全局重定位主要识别区块，随后再按工作范围识别控件，不默认每轮重新枚举整个应用。

程序提供历史描述与合格控件模板匹配线索，Luna结合当前图核对。未匹配到不能直接判为新身份；外观匹配也不等于语义或前景已确认。

### 3.3 复用身份，并保留每次不同的观察

图2、图3、图5的New Alarm沿用同一区块身份r0014，但画面并不完全相同：星期选择及tooltip发生变化，菜单出现后又收起。框架保留历次观察，不能用最后一张图覆盖掉这些历史。

Ring Duration选择器属于New Alarm（c0044），展开后的选项菜单另有区块r0015。二者有关联，但不是同一个控件或同一个观察对象。

### 3.4 区分可见证据、身份模板与点击范围

图3中的Sunday提示可提供星期含义线索，同时遮住了局部界面。它不影响本例Ring Duration入口的可见位置，但也不能因此把被遮挡部分保存成清晰身份模板。发现阶段需取得的身份外观若被遮挡，应转相应恢复；动作阶段则检查是否影响本次目标。

身份裁图用于以后认出控件，点击范围表示当前实际可操作区域；二者分别记录，不能用一个框代替所有用途。原始整图始终作为观察证据保留。

## 4. 第二阶段：从“看见控件”到“有目的地操作”

### 4.1 生成探索任务，不机械遍历全部按钮

仍看图3。真实任务“查看 Ring Duration 可见选项”说明：当前值已知为5 minutes，但候选时长未知，所以展开查看即可，不选择新值。任务目的与图4提供的结果直接对应。

同一New Alarm区块中，名称输入、当前小时/分钟、Add等有仅记录任务；Ring Duration与Snooze Duration形成参数调查任务。**仅记录表示保留可见能力，不等于执行成功；某项调查完成也不等于创建闹钟完成。**

任务清点还会检查控件是否遗漏。发现缺项时回第一阶段补登记；存在前置条件时保留准备任务与原目标，准备完成后仍需判断原任务。

### 4.2 区分工作区块与当前前景

在本例a0034中，探索任务归New Alarm的Ring Duration控件，展开后当前观察对象则是选项菜单。任务归属、现场前景和导航目标需要分别记录，不能因进入菜单就丢掉原调查任务。

任务调度根据原任务状态、当前可交互区块和其他待办决定继续、返回或切换。不是每次进入新界面就自动改写所有工作目标，也不是必须递归完成所有子区块才能结算一次入口观察。

### 4.3 回溯：利用已知关系与当前视觉证据到达目标

本例记录了New Alarm进入Ring Duration菜单，以及菜单收起后恢复New Alarm的实际结果。这样的关系为后续重新到达工作区块提供依据。图5只证明a0035实际返回，**不作为自动回溯已经成功执行的证据**。

一般回溯流程是：确定目标工作区块 → 查找已观察的可用路线 → 在当前图重新定位入口 → 核对当前前景后执行 → 新图检查落点。

已有视觉证据足够时，可尝试程序视觉回溯以减少模型调用；不足时交给重新发现或模型导航。如果后续路线入口已在当前可交互前景，可省掉不必要的前序导航，但不能跳过业务前提。历史路线不是倒序动作列表；从A到B不自动授权从B到A。

### 4.4 投递动作并保存现场

Luna提出一步操作；程序检查动作格式、目标关联及投递前画面，记录提案和回执并保存前后截图。无法可靠关联时不能凭近邻位置伪造身份，是否允许操作按具体路径判断。

以a0034为例，图3为动作前证据，图4为动作后证据，更新阶段据此核对。执行接口成功只说明命令投递情况，不直接决定探索任务或业务目标成功。

## 5. 第三阶段：将观察变成知识，而不是只记一句“成功”

### 5.1 核对结果与任务完成范围

图3→图4表明菜单确实展开。任务要求是查看选项与当前值，因此该任务可以登记done；没有新值选择或提交证据，不能进一步宣布“设置已保存”或“闹钟已添加”。

### 5.2 更新参数与身份，保留来源

Ring Duration原先只记录当前值5 minutes。展开后，其任务发现更新为六个可见候选，条件是“New Alarm对话框中展开Ring Duration选择器时”，并保存a0034与动作后截图为来源。

这也是图3与图4的知识增量：**从知道当前显示什么，变成知道在这个上下文中有哪些可选值。** 框架同时保留早期仅看到5 minutes的观察，不把后来知道的事实倒写成一开始就知道。

### 5.3 整理区块功能

真实记录中，New Alarm区块具有“配置并添加闹钟”功能条目，关联时间、星期、名称和时长等任务及控件。但其完成说明明确保留“尚无提交结果证据”。

功能条目表达可供后续任务构造使用的能力描述；图2—图6这一片段只验证了进入、部分参数观察及取消返回，没有验证提交新增。整理完后，再由调度决定继续哪个任务或区块。

## 6. 一张New Alarm截图，具体会保存成什么

本节以图2—图5为共同例子。下表映射真实字段；说明文字经过整理，**不是伪造一份完整模型原回复**。附带的区块JSON取自同一固定结束快照，因此包含后续累积历史，不能当作图2时刻的知识。

### 6.1 区块本身：不只有名称，还有描述与职责

| 字段 | 本例实际内容或用途 |
|---|---|
| `id` / `name` | r0014 / New Alarm 对话框 |
| `description` | 描述时间、Repeat、Name、Ring/Snooze Duration、Cancel和Add；结束快照还包含当时值和状态 |
| `parent_region` | 保存已确认父区块引用；不能仅因“从Alarms打开”就猜它是Alarms的结构子区块 |
| `observations` | 从初次出现到后续操作的多次观察、描述、理由、图像和来源 |
| `region_role` / `role_evidence` | 功能整理时对区块角色及依据的记录；不是所有区块初次发现就已有 |
| 范围、行为上下文等可选记录 | 存在时表达限定或区分依据，不能推定每个区块都有 |

本例首次观察的描述概括为：**新建闹钟模态对话框，时间17:10，包含星期选择、可选名称、响铃与贪睡时长，以及取消和添加按钮。** 描述帮助模型理解职责和历史候选，但不单独证明身份。区块顶层描述还可能包含一次观察状态，不应当作永久不变的属性。区块完整记录（见本地材料包）

### 6.2 每次观察：同一身份，多个时刻

每条`observations`保存当次`description`、划分理由`reason`、可见控件清点情况`controls_complete`、裁图`image`、质量判断、原图`source_image`及来源`evidence`。

**区块observations不是每张截图的逐帧日志。** 本包r0014显式观察项来自0110/a0031、0116/a0033和0135/a0038；图5/a0035的返回证据在动作记录中，其0120回复没有新增regions条目。图2、图3和图5可通过观察与动作证据共同关联New Alarm身份，但不能声称三张图都新增了一条区块observation。某次`controls_complete=true`也只描述该次可见清单，不证明整个应用或全部隐藏内容已经覆盖。

### 6.3 控件：以Ring Duration为例

New Alarm的`controls`中，c0044为Ring Duration选择器。记录有名称、历次可见文字/外观/状态/可能操作/不确定性，身份图与点击范围，以及`task_refs`和`action_refs`。

| 读者看图 | 记录承担的作用 |
|---|---|
| 图3中“Ring Duration”“5 minutes”和下拉箭头 | 说明这是哪个入口、当前显示什么 |
| 入口外观及可操作行范围 | 分别服务身份识别与动作定位 |
| 图4出现选项菜单 | 与a0034真实动作结果关联，不把菜单所有选项塞成原按钮的身份 |
| 原图与调用来源 | 让名称、位置和结果可以追查，而不是只有最终摘要 |

### 6.4 任务与发现：从未知到完成

真实任务记录的主要内容如下（节选）：

| 字段 | 本例值 |
|---|---|
| `name` / `control` | 查看 Ring Duration 可见选项 / c0044 |
| `handling` / `task_type` | explore / parameter |
| `reason` | 当前显示5 minutes，但候选尚未观察；展开查看，不选择新值 |
| `status` / `attempts` | done / a0034 |
| `findings` | 六个可见时长，当前5 minutes，适用条件及来源 |
| `result_evidence` | 动作后选项列表和勾选标记满足本任务目标 |

区块另有`task_inventory`记录清点范围及依据。清点完整、某个任务done、业务完成，是三个不同判断。

### 6.5 功能：把多个控件与任务组织成能力

`functions`中的“配置并添加闹钟”包含`description`（功能含义）、`object`（待创建闹钟）、`completion`（完成表现与未验证部分）、`task_refs`、`locations`（控件引用）和`constraints`（参数/条件/来源）。

例如，Ring Duration的六个选项进入参数知识；小时17和分钟10只是该次可见值，不能据此推断完整数值范围。**存在功能条目不等于已执行该功能。** 图6的取消返回尤其不能拿来证明Add成功。

### 6.6 动作与关系：保存真实经验

`actions`中的a0034记录来源控件、click操作、投递状态、目的、实际结果、区块变化、当前可交互区块及证据引用。图3/图4分别是它的前后图。

`transitions`保存观察到的出口关系；`reached_by`记录到达来源。例如New Alarm经c0044/a0034到Ring Duration菜单。它们引用实际动作，供导航使用；到达来源不是自动生成的反向操作。区块内部参数变化可以保留在动作结果中，不必制造一条导航自环。

### 6.7 运行状态：单独保存“现在要做什么”

`runtime_state`保存`working_region`（工作区块）、`interactive_regions`（当前可交互区块）、活动任务（存在时）、观察、下一阶段、导航交接及纠错信息。

图4说明为什么需要分开：调查任务属于New Alarm的选择器，但当时展开的是参数菜单。附带的runtime-state.json（见本地材料包）是结束快照，不是图4当时状态；它用于说明实际字段，不能据此复原图4时刻的全部调度选择。

### 6.8 磁盘上的组织方式

以下是目录结构示意，尖括号代表具体运行中的编号或快照名：

```text
run/
├─ knowledge_current.json                 当前知识快照入口
├─ knowledge_snapshots/<snapshot>/
│  ├─ regions/<region>/region.json         描述、观察、控件、任务、功能、动作与关系
│  ├─ regions/<region>/images/             本快照产生的相关裁图（按需存在）
│  └─ runtime_state.json                   工作目标、当前前景及下一阶段
├─ calls/<call>/                          请求、回复及相关提示
├─ action_attempts/<attempt>/             提案、回执、执行前后图
├─ navigation_replays/                    视觉导航记录
├─ recovery_episodes/、repair_episodes/    恢复与纠错证据
└─ step_rounds/                           轮次、结果及预算记录
```

新登记发布新知识快照，旧记录保留；图片可以引用历史快照或原始动作目录，不要求每次复制整套图像。内部编号用于程序关联，不默认原样发送给模型。模型输入按阶段选择当前截图、相关描述、任务和历史，不是每次发送整库。

## 8. 框架介绍后，如何衔接宏观问题

通过上面的具体过程，可以把问题归到三类，而不是逐个罗列小补丁：

| 宏观问题 | 对应框架部分 | 需要回答的问题 |
|---|---|---|
| 界面理解与知识一致性 | 第一阶段身份识别、第三阶段更新、区块存储 | 画面变化后还能否正确区分原对象、新对象和状态变化？ |
| 探索目标与推进策略 | 任务清点、前置条件、调度、功能整理 | 哪些未知值得调查，怎样减少回访和重复整理，何时算足够？ |
| 连续执行与恢复可靠性 | 识别→动作交接、回溯、纠错和恢复 | 单步能工作之后，能否持续推进并从局部失败中恢复？ |

主例已经证明局部参数观察和取消返回可完成；同一续跑段最终仍以`correction_blocked`结束（阶段统计（见本地材料包）），因此不能将这组顺利片段当作整个探索过程稳定的证明。本节只给宏观定位，具体故障与修复状态应在后续问题部分展开。
