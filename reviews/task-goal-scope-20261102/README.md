## 实际验证

使用两份独立完整真实记录副本，沿正常框架构造请求、发送 Luna，并将未经编辑的回复送入正常校验、纠错和登记路径。两个实际发送的提示均包含用户逐字定义，没有本批应用特定正例。总计 2 次模型调用、0 次纠错、0 次新 GUI。

| 案例 | 实际结果 | 判断 |
| --- | --- | --- |
| 提出任务 | 生成并登记11个function任务，类型和对象身份正确；每项均预加“若有子菜单，查看其可见选项以确认可到达的功能” | 仍把独立子菜单问题提前纳入入口条件，不接受 |
| 结算已有任务 | 已接受知识及展开菜单截图足以回答人工收窄的原问题，answered正常登记done；其它10项保留 | 仅该原问题结算通过 |

两例不能拼为新生成任务的成功闭环：结算例使用人工收窄的条件，不是提出例的新条件。不能据两次调用认定纠错率下降，也没有本轮新导航成功的证据。原动作仍有登记缺口，结算不代表动作补登记。

原现场11项任务条件由操作员修订，历史值和状态保留；模型只修改测试副本。原现场仍10 pending、1 blocked，没有部署或恢复遍历。

独立审阅先读取完整提示与截图，再核对原答和登记、最后与用户意图比较，结论相同：结算样本通过，提出范围未通过。截图、完整请求/回复、对象记录及私人路径未公开；它们保留在本地便携评审包中。
