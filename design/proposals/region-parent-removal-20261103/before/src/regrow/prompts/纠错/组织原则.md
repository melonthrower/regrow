# 纠错 Prompt 组织原则

纠错仍是原业务调用的延续。组织顺序围绕“哪里需要改、依据什么改、修改哪份回复”。

1. **身份稳定**：system 保留原角色和运行范围，各出现一次。
2. **问题明确**：system 用一句话说明当前修正任务；user 开头给出最新错误的对象、字段和具体原因。
3. **材料完整、层次分明**：概念和字段含义在 system 的业务参考中；原任务、对象记录、实际动作、历史和截图在 user 的原任务材料中。旧问题标为参考，不与当前修正任务并列。
4. **修改对象唯一**：user 最后给一份待修正回复。缺单个值补占位词；缺整段对象或列表，用固定字段结构和占位词补入，已有输入值保留。类型或语义错误给具体要求，不用虚构事实充当例子。
5. **输出沿用原合同**：普通重答返回原格式完整 JSON；仍需观察、修改历史记录等处理方式的专门纠错保留自身合同。格式校验失败也按该次实际合同修正。

## 本次实现

普通重答 system：角色和范围 → `修正标出的问题，其余内容保留。返回完整 JSON。` → 原调用业务参考。

user：本次问题 → 必要的本次补充材料 → 原任务与相关材料 → 待修正回复。

缺失字段的提示结构只在缺失处补占位。模板由字段占位.json维护；同名字段在不同调用中可能是对象或列表，按本次response_schema调整容器形状并过滤不允许的键。模板不推断实际值。task_update的条件字段在占位中说明何时填写、何时省略。这里的“保留”是输入构造保证与输出指令，不是对 Luna 回答的强制局部合并；回复仍经过原校验和登记。

本次保留原调用业务参考和历史，没有实现按错误字段自动裁剪历史。角色和范围已有文案内部的重复，也不在本次重写范围内。

## 修改位置

|修改内容|维护文件|

概念含义仍修改原调用及对应对象说明，不在纠错中另写一套定义。应用名、控件名与实际错误由运行材料提供，不写入通用模板。

## 错误类型与处理入口

缺字段、错误引用、重复登记、列表分组和本次归属/父子结构冲突，只需改当前回复时均使用原格式重答；各业务模块继续负责检查并提供错误原因。填错值保留在原答中，缺失值才补占位。功能/参数引用的部分诊断仍是文字异常，不妨碍进入同一重答步骤，但不等于都已有统一字段路径。

若冲突涉及历史记录的修订、补观察或身份/操作目标视觉判断，保留原专门处理能力。规则只能识别其覆盖的结构或引用冲突，不能自动发现所有语义归属错误。

本轮为task_update、action_result、bbox、foreground、next_action、previous_regions、knowledge、local_knowledge及若干字符串列表提供固定结构。其他同名字段可能有不同业务形态，不能声称所有动态结构都已覆盖；新增结构先核对现有调用合同。
